## 一、分析框架

### 1.1 痛点分析模型

每个功能按以下结构分析：

```
┌─────────────────────────────────────────────────────────────────┐
│  用户场景 → 痛点描述 → 当前方案 → 优化方向 → 预期效果           │
└─────────────────────────────────────────────────────────────────┘
```

### 1.2 痛点严重度评估

| 等级 | 说明 | 优先级 |
|------|------|--------|
| P0 | 阻断用户完成核心任务 | 立即解决 |
| P1 | 影响用户体验，导致流失 | 本版本解决 |
| P2 | 体验优化，提升满意度 | 下版本解决 |
| P3 | 锦上添花 | 远期规划 |

## 二、认证模块

### 2.1 Passkey 注册

#### 用户场景
> 小王（28 岁，互联网公司运营）在朋友圈看到朋友分享的诗词卡片，想下载晓诗体验。

#### 痛点分析

| 痛点 | 描述 | 严重度 |
|------|------|--------|
| **注册成本高** | 传统注册需要：手机号 → 收验证码 → 设置密码 → 确认密码，至少 4 步 | P1 |
| **密码焦虑** | 用户记不住密码，或担心密码泄露 | P1 |
| **流失率高** | 每多一步操作，流失率增加约 20% | P0 |

#### 当前方案（已实现零输入）

```
传统注册（4 步）                    Passkey 注册（零输入）
┌─────────────────────┐            ┌─────────────────────┐
│ 1. 输入手机号        │            │ 1. 点击「注册」       │
│ 2. 获取验证码        │            │ 2. 浏览器指纹/面容    │
│ 3. 设置密码          │            │    ↓                 │
│ 4. 确认密码          │            │    注册完成 ✓        │
│    ↓                 │            └─────────────────────┘
│    注册完成 ✓        │
└─────────────────────┘
  耗时：30-60 秒                       耗时：5-8 秒
  流失率：~40%                         流失率：~10%
  用户输入：4 项                        用户输入：0 项（自动检测设备名）
```

**实现方式**：前端通过 `detectDeviceName()` 自动从 `navigator.userAgent` 检测设备类型：
```typescript
// 自动检测示例
"Chrome on Mac"      // Mac 上的 Chrome
"Safari on iPhone"   // iPhone 上的 Safari
"Firefox on Windows" // Windows 上的 Firefox
```

#### 优化方向

| 优化项 | 说明 | 预期效果 |
|--------|------|----------|
| **设备名可编辑（Profile）** | 在个人中心允许用户修改自动生成的设备名（如改为「小王的 MacBook」） | 个性化 |
| **浏览器兼容性提示** | 检测到不支持 Passkey 的浏览器时，提前引导切换，而非报错后才知道 | 减少挫败感 |
| **进度可视化** | 注册过程中显示「正在创建安全密钥...」明确反馈，避免用户以为卡了 | 减少焦虑 |
| **备选登录方式** | Passkey 失败时提供微信/Apple 登录兜底（v1.1） | 覆盖 100% 场景 |

#### 验收指标

- 注册转化率 ≥ 60%（行业平均 30%）
- 注册完成时间 ≤ 8 秒
- 注册流失率 ≤ 15%
- **用户输入项 = 0**（核心指标）

### 2.2 Passkey 登录

#### 用户场景
> 小王每天打开晓诗读诗，希望像打开微信一样「秒进」。

#### 痛点分析

| 痛点 | 描述 | 严重度 |
|------|------|--------|
| **每日登录摩擦** | 传统登录需要：输入账号 → 输入密码 → 点击登录，每天重复 | P0 |
| **密码遗忘** | 如果不常使用，容易忘记密码，需要「找回密码」流程 | P1 |
| **登录意愿下降** | 每次登录的摩擦会降低用户打开 App 的频率 | P0 |

#### 当前方案（已实现零输入）

```
传统登录                            Passkey 登录（零输入）
┌─────────────────────┐            ┌─────────────────────┐
│ 1. 输入邮箱/手机     │            │ 1. 点击「使用 Passkey │
│ 2. 输入密码          │            │    登录」            │
│ 3. 点击登录          │            │ 2. 浏览器指纹/面容    │
│    ↓                 │            │    ↓                 │
│    登录完成 ✓        │            │    登录完成 ✓        │
└─────────────────────┘            └─────────────────────┘
  耗时：10-15 秒                       耗时：3-5 秒
  心理成本：高                         心理成本：极低
  用户输入：2 项（账号+密码）            用户输入：0 项
```

#### 优化方向

| 优化项 | 说明 | 预期效果 |
|--------|------|----------|
| **自动登录检测** | 检测到已有 Passkey 时，自动弹出验证，无需点击按钮 | 再省 1 步 |
| **Token 智能续期** | 活跃用户 Token 自动续期，7 天内无需重新登录 | 无感登录 |
| **多设备同步** | 在一台设备登录后，其他设备可快速同步（跨设备 Passkey） | 多设备无缝 |
| **生物识别优先** | 支持 Face ID / Touch ID / Windows Hello，而非仅密码 | 体验提升 |

#### 验收指标

- 登录转化率 ≥ 90%
- 登录完成时间 ≤ 5 秒
- 7 日留存提升 ≥ 15%（对比传统登录）
- **用户输入项 = 0**（核心指标）

### 2.3 跨设备添加 Passkey

#### 用户场景
> 小王买了新 iPad，想在平板上也能用晓诗读诗，不想重新注册账号。

#### 痛点分析

| 痛点 | 描述 | 严重度 |
|------|------|--------|
| **设备迁移成本** | 新设备需要重新注册或登录，Passkey 不具备跨设备能力 | P1 |
| **多设备管理** | 用户有手机 + 平板 + 电脑，需要在每台设备上单独注册 | P1 |
| **账号孤岛** | 不同设备上的数据不同步，阅读进度丢失 | P0 |

#### 当前方案

```
设备 A（已登录）                           设备 B（新设备）
    │                                         │
    ├── 点击「添加新设备」                     │
    ├── 生成 QR 码 ─────────────────────────→ │ 扫码
    │                                         │
    ├── 等待确认 ←─────────────────────────── │ 确认连接
    │                                         │
    ├── 点击「确认」 ───────────────────────→ │ 浏览器弹窗
    │                                         │ 创建 Passkey
    │← 绑定完成                                │
```

#### 优化方向

| 优化项 | 说明 | 预期效果 |
|--------|------|----------|
| **QR 码自动刷新** | QR 码 5 分钟自动刷新，避免过期后重新生成 | 减少操作步骤 |
| **推送通知确认** | 设备 A 收到推送通知，点击即可确认，无需打开 App | 确认时间从 30s → 5s |
| **设备命名智能建议** | 自动建议「小王的 iPad」「小王的 MacBook」 | 便于管理 |
| **设备管理面板** | 统一管理所有设备，支持远程解绑丢失设备 | 安全性提升 |

## 三、每日一诗模块

### 3.1 每日推荐

#### 用户场景
> 小王每天早上通勤路上，想花 3 分钟读一首诗，但不知道读什么好。

#### 痛点分析

| 痛点 | 描述 | 严重度 |
|------|------|--------|
| **选择困难** | 面对海量诗词，不知道今天该读哪首 | P0 |
| **决策疲劳** | 每次打开 App 都要搜索/浏览，消耗意志力 | P0 |
| **内容不匹配** | 推荐的诗可能太难/太简单/用户已经读过 | P1 |
| **缺乏仪式感** | 没有「今日专属」的感觉，像在数据库里翻 | P1 |

#### 当前方案

```
每日一诗推荐流程
┌─────────────────────────────────────────────────────────────────┐
│                                                                 │
│   用户打开 App                                                   │
│        │                                                        │
│        ▼                                                        │
│   后端算法选择今日诗歌                                            │
│   （基于日期/用户偏好/热度）                                      │
│        │                                                        │
│        ▼                                                        │
│   首页展示完整诗歌卡片                                            │
│   · 渐变顶边装饰                                                 │
│   · 标题 + 作者                                                  │
│   · 正文（宽松行高）                                             │
│   · 译文（折叠）                                                 │
│   · 赏析（折叠）                                                 │
│   · 标签                                                        │
│        │                                                        │
│        ▼                                                        │
│   用户直接阅读，零决策成本                                        │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
```

#### 优化方向

| 优化项 | 说明 | 预期效果 |
|--------|------|----------|
| **智能推荐算法** | 基于用户历史（收藏/打卡/跳过）个性化推荐 | 点击率提升 30% |
| **难度适配** | 根据用户阅读水平推荐合适难度的诗 | 减少挫败感 |
| **节日/时令联动** | 中秋节推荐月亮诗，清明节推荐相关诗 | 文化共鸣 |
| **每日一诗推送** | 每日早 8 点推送，无需主动打开 App | 提升 DAU |
| **「换一首」按钮** | 不满意可换一首（每日限 3 次） | 控制感提升 |
| **日历视图** | 查看过去 7/30 天的每日诗歌 | 补读场景 |

#### 验收指标

- 首页阅读率 ≥ 70%（用户打开后实际阅读）
- 平均阅读时长 ≥ 2 分钟
- 「换一首」使用率 ≤ 20%（过高说明推荐不准）

### 3.2 拼音标注

#### 用户场景
> 小王读到一首诗里有不认识的生僻字（如「爝」「燮」），影响理解。

#### 痛点分析

| 痛点 | 描述 | 严重度 |
|------|------|--------|
| **生僻字障碍** | 古诗词中常见生僻字，用户不认识就读不下去 | P0 |
| **读音不确定** | 多音字（如「长」「行」）不知道诗中读什么 | P1 |
| **音韵美缺失** | 用户想感受诗词的音韵美，但不知道正确读音 | P2 |

#### 当前方案

```
拼音关闭状态                    拼音开启状态
┌─────────────────────┐        ┌─────────────────────┐
│                     │        │                     │
│   静夜思            │        │   静夜思            │
│   唐·李白           │        │   唐·李白           │
│                     │        │                     │
│   床前明月光，      │        │   chuáng qián       │
│   疑是地上霜。      │        │   míng yuè guāng，  │
│   举头望明月，      │        │   yí shì dì shàng  │
│   低头思故乡。      │        │   shuāng。          │
│                     │        │   ...               │
└─────────────────────┘        └─────────────────────┘
```

#### 优化方向

| 优化项 | 说明 | 预期效果 |
|--------|------|----------|
| **拼音准确性提升** | 多音字根据上下文自动选择正确读音（如「长」在「长风」读 cháng，在「生长」读 zhǎng） | 减少错误 |
| **拼音位置调整** | 支持「上方标注」「右侧标注」「隐藏」三种模式 | 满足不同偏好 |
| **声调颜色化** | 四声用不同颜色标注（一声红、二声橙、三声绿、四声蓝） | 视觉辅助 |
| **点击发音** | 点击汉字播放真人发音（v2.0） | 听觉辅助 |
| **拼音字体优化** | 拼音字体与汉字视觉协调，不突兀 | 美观度提升 |

#### 验收指标

- 拼音开启率 ≥ 40%（衡量需求强度）
- 拼音准确率 ≥ 99%
- 多音字正确率 ≥ 95%

### 3.3 简繁切换

#### 用户场景
> 小王是港澳台用户，习惯读繁体字；或者小王想通过读繁体感受古典韵味。

#### 痛点分析

| 痛点 | 描述 | 严重度 |
|------|------|--------|
| **繁体用户排斥** | 港澳台/海外华人习惯繁体，简体让他们不适 | P1 |
| **简繁混用** | 大陆用户偶尔也想读繁体，感受原版 | P2 |
| **学习需求** | 一些用户想通过阅读繁体学习认字 | P2 |

#### 当前方案

```
简体模式                          繁体模式
┌─────────────────────┐        ┌─────────────────────┐
│                     │        │                     │
│   静夜思            │        │   靜夜思            │
│   唐·李白           │        │   唐·李白           │
│                     │        │                     │
│   床前明月光，      │   ↔    │   床前明月光，      │
│   疑是地上霜。      │        │   疑是地上霜。      │
│   举头望明月，      │        │   舉頭望明月，      │
│   低头思故乡。      │        │   低頭思故鄉。      │
│                     │        │                     │
└─────────────────────┘        └─────────────────────┘
```

#### 优化方向

| 优化项 | 说明 | 预期效果 |
|--------|------|----------|
| **全局持久化** | 切换后所有页面同步，无需每页重新设置 | 体验一致性 |
| **切换动画** | 简繁切换时带淡入动画，减少视觉跳跃感 | 体验流畅 |
| **默认偏好记忆** | 记住用户上次选择，下次打开自动应用 | 减少操作 |
| **地区自动检测** | 根据 IP/系统语言自动推荐初始模式 | 首次体验优化 |

### 3.4 竖排阅读

#### 用户场景
> 小王想体验古人从右到左、从上到下的传统阅读方式。

#### 痛点分析

| 痛点 | 描述 | 严重度 |
|------|------|--------|
| **传统阅读体验缺失** | 现代横排无法感受古典诗词的原始排版 | P2 |
| **沉浸感不足** | 横排阅读缺乏「古风」仪式感 | P2 |
| **教育场景** | 语文老师需要竖排展示给学生看 | P1 |

#### 当前方案

```

```

#### 优化方向

| 优化项 | 说明 | 预期效果 |
|--------|------|----------|
| **竖排时自动隐藏拼音** | 竖排模式下拼音排版混乱，自动隐藏 | 体验一致性 |
| **标点符号适配** | 竖排时标点符号位置正确（如句号在字右侧） | 专业度提升 |
| **行间距优化** | 竖排行间距略大于横排，便于阅读 | 可读性提升 |
| **标题竖排** | 标题也支持竖排，整体统一 | 沉浸感提升 |

## 四、阅读计划模块

### 4.1 创建计划

#### 用户场景
> 小王想系统地读完《唐诗三百首》，希望有个计划帮他安排每天读什么。

#### 痛点分析

| 痛点 | 描述 | 严重度 |
|------|------|--------|
| **缺乏规划** | 想系统读诗但不知道如何安排进度 | P0 |
| **选择困难** | 不知道该先读哪些诗、按什么顺序读 | P0 |
| **难以坚持** | 没有计划容易三天打鱼两天晒网 | P0 |
| **进度不清晰** | 不知道自己读了多少、还剩多少 | P1 |

#### 当前方案

```
创建计划流程
┌─────────────────────────────────────────────────────────────────┐
│                                                                 │
│   1. 填写计划信息                                                │
│      · 计划名称（如「唐诗三百首」）                               │
│      · 描述                                                    │
│      · 标签                                                    │
│                                                                 │
│   2. 添加诗歌                                                   │
│      · 搜索诗歌（实时搜索）                                      │
│      · 添加到列表                                               │
│      · 拖拽排序                                                 │
│                                                                 │
│   3. 设置参数                                                   │
│      · 每日篇数（1-50）                                         │
│      · 开始日期                                                 │
│                                                                 │
│   4. 发布                                                       │
│      · 保存到「我的计划」                                        │
│      · 可选：发布到「诗林」                                      │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
```

#### 优化方向

| 优化项 | 说明 | 预期效果 |
|--------|------|----------|
| **模板计划** | 提供预设模板（唐诗三百首、小学生必背 75 首、宋词精选） | 降低创建门槛 |
| **智能排序** | 按难度/作者/主题自动排序，用户可微调 | 减少决策 |
| **计划预览** | 发布前预览完整计划（每天读什么） | 减少错误 |
| **计划分享** | 一键生成分享卡片，吸引朋友加入 | 社交裂变 |
| **计划克隆** | 看到好的计划可以「克隆」到自己的账号 | UGC 激励 |

#### 验收指标

- 计划创建完成率 ≥ 50%（开始创建后实际完成）
- 模板使用率 ≥ 30%
- 计划发布到诗林的比例 ≥ 20%

### 4.2 订阅计划

#### 用户场景
> 小王在诗林看到一个「每日一诗·365 天」计划，觉得很适合自己，想订阅。

#### 痛点分析

| 痛点 | 描述 | 严重度 |
|------|------|--------|
| **发现困难** | 诗林计划多，不知道哪个适合自己 | P1 |
| **决策成本高** | 不确定计划质量，怕订阅后不适合 | P1 |
| **切换成本** | 订阅后想换计划，之前的进度丢失 | P1 |

#### 当前方案

```
订阅流程
┌─────────────────────────────────────────────────────────────────┐
```

|------|------|--------|
| **LIKE 查询慢** | `WHERE title LIKE '%keyword%'` 无法使用索引，全表扫描 | P0 |
| **中文分词难** | PostgreSQL 默认不支持中文分词 | P1 |
| **简繁不通** | 搜简体搜不到繁体 | P1 |

#### 优化方案

```sql
-- 1. 启用扩展
CREATE EXTENSION IF NOT EXISTS pg_trgm;
CREATE EXTENSION IF NOT EXISTS zhparser;

-- 2. 创建 trigram 索引
CREATE INDEX idx_poems_title ON poems USING gin (title gin_trgm_ops);
CREATE INDEX idx_poems_title_sc ON poems USING gin (title_sc gin_trgm_ops);
CREATE INDEX idx_poems_author ON poems USING gin (author gin_trgm_ops);
CREATE INDEX idx_poems_author_sc ON poems USING gin (author_sc gin_trgm_ops);

-- 3. 简繁通搜查询
SELECT * FROM poems
WHERE title ILIKE '%keyword%'
   OR title_sc ILIKE '%keyword%'
   OR author ILIKE '%keyword%'
   OR author_sc ILIKE '%keyword%'
ORDER BY similarity(title, keyword) DESC
LIMIT 20;
```

#### 预期效果

- 搜索响应时间：从 2000ms → < 200ms（1 万条数据）
- 支持简繁体混合搜索
- 支持模糊匹配（错别字容错）

### 11.2 打卡并发

#### 痛点分析

| 痛点 | 描述 | 严重度 |
|------|------|--------|
| **重复打卡** | 用户快速点击多次，导致重复记录 | P1 |
| **并发冲突** | 同一用户多设备同时打卡 | P1 |

#### 优化方案

```sql
-- 唯一约束：每天每用户只能打卡一次
ALTER TABLE checkins ADD CONSTRAINT uk_checkin_user_date
    UNIQUE (user_id, date);

-- 插入时忽略重复
INSERT INTO checkins (user_id, subscription_id, poem_id, date)
VALUES ($1, $2, $3, CURRENT_DATE)
ON CONFLICT (user_id, date) DO NOTHING;
```
